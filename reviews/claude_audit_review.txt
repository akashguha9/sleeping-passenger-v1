# D. Where Codex Is Overengineering

**The module count.** Eight new scripts + nine test files + five config files + SQLite + two constants + five file modifications. Even if every item is individually correct, the aggregate is a V2 not a V1. You are a solo operator. A milestone this size will take weeks and will not be testable as a unit until the final piece lands. That's the opposite of the observation-first discipline.

**The table schema for chronology_events is too rich for V1.** Fields like `source_id`, `account_id`, `score`, `threshold`, `payload_ref`, `evidence_json` are all defensible in isolation, but together they create a data model that you'll have to populate correctly before you've observed what's actually needed. A three-column minimum — `candidate_id`, `stage`, `timestamp` — gets you 80% of the value. The rest can be added when you've logged your first 50 candidates and seen what's missing.

**The signal_vocoder.py modification.** Codex says "modify signal_vocoder.py:1249 so observation mode cannot consume synthetic fallback." This is a defensive change to a file that's not in the observation path. If the observation branch doesn't import signal_vocoder, it can't accidentally consume synthetic fallback. The defense lives at the import boundary of the new subsystem, not by modifying the existing one. This is exactly the kind of "protect against a failure mode that can't occur" that bloats MVP work.

**Observation freshness and sample counts in the health report.** Adding observation subsystem state into the health report output before the observation subsystem has produced any meaningful output is putting the read surface in front of the data. Build the subsystem, let it log for a month, and *then* decide what needs to surface in the health report. Pre-wiring the surface is speculative.

**Nine new test files.** You do not need `test_asset_attachment_detector.py`, `test_commitment_detector.py`, `test_market_confirmation_detector.py`, `test_pattern_classifier.py`, `test_backfill_adapter.py`, and `test_run_observation_cycle.py` before any of those detectors exist. One integration test for the chronology store plus one null-case test is enough for the first slice. Each detector gets its own test when it's built, one at a time.

**Pre-specifying five pattern classes (A, B, D, H_T3_ONLY, NULL_TIMEOUT).** This is fine as a future direction but premature as code. The pattern classifier in V1 should output a single string field — "the observed ordering as a tuple" — and let downstream analysis decide what to label it. Hardcoding pattern class enums before observing real data is exactly the sample-size trap Codex warns against in section L and then falls into in section D.

**Pre-writing the Intent Reconstruction Engine classification taxonomy (observe, announce_position, persuade, warn, pump-risk).** Codex correctly flags Intent Reconstruction as PARTIALLY_PRESENT and says "use: LOG_ONLY," but then specifies the taxonomy up front. Don't. Log raw text with source metadata. Taxonomize later from real observations. Pre-specified taxonomies are how you end up with a tagging system that doesn't match what you actually see.
